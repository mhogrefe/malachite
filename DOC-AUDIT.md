# Documentation audit: correctness of every doc block, complexity claim, and scratch bound

Instructions for a multi-session campaign, written 2026-08-03. The goal: every documentation
block in the four main crates is verified against the code it describes, every complexity claim
carries an argument for why it is accurate, and every scratch-buffer requirement is rederived
from the implementation. Read this whole document before starting a chunk.

Complexity claims include both the "Worst-case complexity" and (for random generators) the
"Expected complexity"/"Expected complexity per iteration" headers.

Two forms of leverage make this smaller than it looks:

- **Macro sharing.** Doc blocks generated by impl macros or doc macros
  (`apply_to_unsigneds!`-style families, `natural_mod_sqrt_doc!`-style shared docs) are audited
  once per macro, then every instance's checkbox may be ticked. Most of malachite-base is like
  this.
- **Delegation.** A wrapper whose body is a single call inherits its callee's complexity; once
  the callee is audited, the wrapper's audit is only "does the claim match the callee's, with
  variables renamed correctly?"

## What "audited" means for one item

Check the box only when all of the following have been verified against the implementation:

1. **Description and formula.** The prose says what the function does, including rounding
   directions, sign conventions, edge cases (zero, negatives, empty slices), and ownership
   phrasing. The $f(x, y) = \ldots$ LaTeX is correct.
2. **Panics.** Every claimed panic is reachable; every unconditional panic or assert in the
   function (or its unconditional callees) is claimed. Debug-only asserts are not documented.
3. **Complexity.** The $T$ and $M$ claims are correct, every variable appearing in them is
   defined in the `where` line, the definitions are the right ones (e.g. `n` is the bit length
   of the correct operand), and an accuracy argument is recorded per the convention below.
4. **Examples.** Doctests execute (so they are correct); check that they exercise the
   interesting cases the prose mentions.
5. **Scratch (items tagged `scratch`/`slen`).** See the next section.

Findings are fixed immediately, with the usual per-session verification (tests for behavioral
fixes, `rundoc.sh` for doctest changes, the lint sweep). Every finding, even ones fixed on the
spot, is recorded in the findings log at the bottom of this file: the pattern of what tends to
be wrong is itself a product of the audit.

## The complexity model (settle during the pilot, then write down once)

Many arguments become one-liners once the model is stated in a single place (proposed: a
`# Complexity conventions` section in each crate's top-level docs, written during the pilot):

- Word-RAM with `Limb`-sized words; $T$ counts limb operations, $M$ counts additional limbs.
- What $n$ means by default (`significant_bits` for bignum inputs, slice lengths for limbs
  functions), and that multiplication cost is written explicitly as
  $O(n \log n \log\log n)$.
- **The width-stability rule for primitive-int functions** (settled with Mikhail 2026-08-03,
  resolving the mod_sqrt-vs-mod_pow inconsistency in mod_pow's favor). Since primitive inputs
  are bounded, everything is technically $O(1)$; the honest rule is to analyze each function
  *as if generic over the width $W$* — which it literally is, being macro-generated over
  `u8`..`u128`:
  - Claim **"Constant time and additional memory"** only when the operation count is bounded
    by a constant independent of both $W$ and the input values: straight-line code, fixed
    trip-count loops, and single machine ops (add, mul, div, popcount, clz; `u128` ops count
    as $O(1)$ too, being a fixed number of native ops).
  - Otherwise state the real driver: $n = $ `x.significant_bits()` (or similar) when the trip
    count tracks an input's value, $W$ (the type's width) when it tracks the width regardless
    of value (e.g. a loop over all bits). Equivalently: the claim must stay correct if the
    same algorithm were instantiated at a larger width.
  - A one-time note in the conventions section says that for primitives these variables are
    bounded by $W$, so callers may read every such bound as a constant if they wish.
  - Test: primitive `mod_pow` is $T(n) = O(n)$, $n$ = exponent bits (correct today);
    primitive `mod_sqrt`'s "constant time" claim is a **finding** — Tonelli–Shanks is
    $O(n^2)$ modular ops in the worst case, $n$ = modulus bits, and the nonresidue search is
    value-dependent.

## Complexity-accuracy arguments

(Settled with Mikhail 2026-08-03: leaf-algorithms-only.)

- **Leaf algorithms** (an actual loop/recursion, not a delegation): one to three sentences in
  the doc block (public items) or internal comment (`limbs_*` items) stating the recurrence or
  dominant cost and why it solves to the claimed bound. Ported functions may cite the upstream
  source's analysis.
- **Delegators**: no argument; the audit only confirms the claim equals the callee's with
  correct variable translation.
- **"Constant time" claims**: no argument, but the audit confirms no hidden input-dependent
  loop (watch for value-dependent searches, as in the quadratic-nonresidue search).

## Scratch-requirement rederivation

The highest-value target: under-sized scratch formulas are a real, observed bug class (the
`limbs_mul_high_same_length_scratch_len` under-sizing found 2026-08-02 returned far less than
the Toom-band recursion consumed). For each of the 61 `*_scratch_len` functions and each of the
108 scratch-taking functions:

1. **Rederive** the peak scratch consumption from the implementation, including recursive
   calls, threshold-dependent branches (schoolbook/Toom/FFT bands!), and any slack the code
   assumes. Record the derivation as an internal comment next to the formula: what each summand
   pays for, and whether the result is exact or an upper bound (say which).
2. **Canary-verify the high-risk families** (settled with Mikhail 2026-08-03: canaries for
   the mul/div heartland only — `toom.rs`, `fft.rs`, `mul_low`/`mul_high`/`mul_mod`,
   `div_exact`, `div_mod`, `half_gcd`; simpler formulas rely on the derivation alone). Add or
   extend tests that fill the scratch with a sentinel, run the function across a size sweep
   straddling every algorithm threshold, and check the touched high-water mark against the
   formula (both directions: no overflow, and flag gross over-allocation). The 2026-08-02
   `mul_high_tests` module is the model.
3. Functions whose requirement is documented only in prose ("`scratch` must have length at
   least ...") get the same treatment; consider promoting recurring prose bounds to
   `*_scratch_len` functions where callers duplicate the arithmetic.

Threshold boundaries deserve special attention: the observed bug lived exactly in the band
between two algorithms, where the tested sizes never landed.

## Verification aids

- **Empirical scaling checks**: not part of the default bar (settled 2026-08-03); reserve
  for cases where a reading is genuinely inconclusive, and give the usual benchmarking
  heads-up first.
- **Mechanical well-formedness lint** (build during the pilot): every complexity block has
  both $T$ and $M$, a `where` line, and every variable used in the formulas is defined in it;
  every documented panic message matches an assert. This catches a whole class of errors
  cheaply and keeps the audited state from regressing. Candidate home: `additional-lints.sh`
  as a Python check, like `unincluded-files.py`.

## Known-suspect list (check early, they seed the findings log)

- FFT multiplication claims ($T$ and especially $M$) versus what `fft.rs` actually allocates.
- Ziv-loop float functions: worst-case versus expected time; whether claims account for the
  precision-doubling loop and for exponent-magnitude dependence, not just `prec`.
- Two-variable claims $T(n, m)$: whether `n` and `m` are attached to the right operands
  (several were written by analogy with neighbors).
- Division family: balanced vs unbalanced cases quoting the same bound.
- "Constant time" on width-bounded but value-dependent loops (see model note above).
- `M(n)` on in-place functions that allocate temporaries internally.

   handful of real algorithms (primitive `mod_pow`, `gcd`, sqrt/root, `mod_sqrt`, primes,
   Kronecker, string/digit conversions) get leaf treatment.
2. **nz limbs kernels** (the heart, split into sub-chunks by family, each its own session or
   two, in this order): logic/comparison/shift → add/sub → mul (basecase, Toom family, FFT,
   `mul_low`/`mul_high`/`mul_mod` — the scratch heartland: 18 scratch-takers in `toom.rs`
   alone) → div/div_mod/div_exact/mod_op → sqrt/root → gcd/extended_gcd/half_gcd → modular ops
   (mod_mul/mod_pow) → digits/strings → factorization/primality.
3. **nz public wrappers**: Natural then Integer impl docs (mostly delegation checks plus
   prose/panics accuracy).
4. **malachite-q** (408 items): gcd-dominated claims; `Rational` reduction invariants in prose.
5. **malachite-float** (1476 items): wrappers first, then the Ziv-loop transcendental family
   with the special attention above.
6. **Wrap-up**: conventions doc finalized, well-formedness lint promoted into the sweep,
   findings-log retrospective.
